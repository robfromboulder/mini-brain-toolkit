# Template Drift: Decision Record

## Problem

`create` seeds a brain by copying the toolkit's templates and substituting their placeholders. The copies fall into two kinds. Knowledge files (SCOPE, APPROACH, FINDINGS, the logs, the enforced-terms entries) fill with the project's own content, and differing from the template is their purpose. Procedure files are the template's text with the placeholders filled in, and are meant to stay that way: the session closeout, work setup, work closeout and dream cycle procedures, the template's text in the brain's `CLAUDE.md`, the hook merged into each project repo's `AGENTS.md`, and the prompts in the brain's `README.md`.

When the toolkit fixes a procedure template, every existing brain keeps the old text, and `check` never compares a brain's procedure files with the current templates. Release notes describe each fix without saying how to apply it, so a fix reaches a brain only if its owner copies it in by hand. 0.71's worktree fix to the hook and its per-part routing in session closeout reached brains that way, and 0.72's error-recovery and Phase 4 fixes to the dream cycle do the same. Upgrade steps in the notes would not close the gap: users don't walk releases version by version, and the steps for one release say nothing about a brain several releases behind.

## Preferred approach: `check` compares each procedure file with the current template, two ways

Rob chose this design on 2026-11-07, in place of the three-way merge adopted on 2026-11-05.

**No upgrade takes a manual step.** Rob's rule for every open choice in this item: `create` and `check` carry every upgrade themselves, so no owner reads release notes to bring a brain current. Where a choice is open, the option that leaves the owner no manual step wins.

Under that rule Rob settled two more choices on 2026-11-05. The install lines pin to the newest release, because tracking `main` made every merged PR look like a new toolkit version. A brain's dream cycle prompts a `check` when the toolkit's remote publishes a newer release than the installed one, rather than at every session start or not at all. Claude settled the rest the same way: renamed templates are followed through the install's history, the enforced-terms rules are compared, check 8 moves a split hook paragraph by paragraph, and `create` and `check` keep `archive/` tracked.

**An owner's edits are legitimate, so no version identifies a file's contents.** Rob's reason for refusing every form of version stamp, stated on 2026-11-07: an owner may change a procedure file for their own purpose, and once they have, no release number says what the file holds. `check` therefore reads the file's text against the current template's, not a version lineage or a common ancestor.

Upgrading a brain is always the same act: run `check` and follow its recommendations. For each procedure file the brain holds, `check` pairs each paragraph of the current template with the brain's version of it and labels it. A paragraph the brain holds word for word is current. One it holds no version of is missing, and `check` recommends adding it. One whose brain version appears word for word in some release's template is behind, a toolkit change the brain has not taken, and `check` recommends the current text. A brain paragraph that is a version of no current template paragraph but appears in some release's template is dropped, and `check` recommends removing it. Any other difference is an own edit, reported with both texts for the owner to bring up to date or keep. The release history labels each paragraph on its own, so no single version stands for the file. The walk-through applies a change only where the owner approves. Knowledge files are never compared with a template.

Nothing records a decision. Every `check` reports each own edit and each declined change again, which Rob wants: it gives the owner a recurring chance to ask whether an edit is still needed, or belongs upstream. Offering to file a toolkit issue for an edit the owner keeps because the template broke for them is a follow-up for a later release.

Before comparing, every text is normalized: the brain's lobespace folds back to `<LOBESPACE>`, `<HUB>` reads as `<LOBESPACE>`, the display and lowercase names fill in, and version lines drop. This needs only the brain's lobespace and names, which `check` identifies while orienting. It does not need `create`'s substitution rules, so those rules gain no second copy.

Three constraints the comparison has to respect:

- **A difference is not always drift.** A brain may adapt a procedure on purpose. The behind label separates a missed toolkit change from an own edit paragraph by paragraph, and every own edit is put to the owner rather than overwritten.
- **Filled-in parts survive.** Substituted placeholders, the brain's read index and lobe registry rows, and the template's staged comments that `create` resolves are the brain's own, so they are not compared.
- **A missing procedure file is a maturity question, not drift.** `check` already recommends adopting machinery when the work justifies it, and a brain that never adopted a procedure has no copy to compare.

## Evidence

On 2026-11-05 the comparison was run by script (`MBT_TEMPLATE_DRIFT_EXPERIMENT.py` in this directory) against three brains, using `git merge-file` for the merge:

- **lamarr-brain and mini-subtitle-wizard-brain**, both seeded on 2026-10-21 from the 0.71 templates. The 0.71-to-`main` changes merged into every file except one with no conflicts, and every local change survived: lamarr's clone name `lamarr-brain`, its rewritten maturity comments and read-index purposes, and subwiz's fixed `~/mini-brains/` path and its Codeberg pull-request rule. The one conflict is subwiz's work-setup step 3, which both the brain and PR #20 rewrote.
- **Normalization is required.** Real brains fill placeholders inconsistently: lamarr's session and work closeouts keep `<LOBESPACE>` where it names the owning lobe at runtime, and subwiz's fill it in. Without normalization, lamarr's work closeout raised two false conflicts and twelve false local differences; with it, none.
- **Work setup inlines its scaffolds in more than one shape**: `` ### `<LOBESPACE>_<WORK>_PLAN.md` `` with a `~~~~` or ```` ```` ```` fence, or `### PLAN template`. Once split out by content, both 0.71 brains' scaffolds matched `templates/work/` exactly, apart from subwiz's burndown rule.
- **virtual-view-brain**, which predates 0.70 and is the exemplar the multi-lobe templates were distilled from. Its session closeout matches the 0.70 template exactly, and its other procedure files are heavily adapted: work setup adds a work-item header and a blocked-by field. The merge kept every adaptation and raised four conflicts in work setup, one in work closeout, three in `CLAUDE.md` and one in the README. A reorganized copy therefore needs no separate recognition: it shows up as conflicts for the owner.
- **Inferring the base works.** Scored against each tagged release, lamarr fit 0.71 best (16 differing lines, against 34 for 0.70 and 20 for 0.72), which matches its seed date. For files seeded before the first tag, several commits fit equally well; any of them gives the same merge.
- **The hook needs no drift update after 0.71.** Its text is unchanged from 0.71 to `main` apart from the merge comment, so the 0.73 hook change is only check 8's move. lamarr's hook is split across two sections of its project `CLAUDE.md` and one rule sits in another list, so the hook's paragraphs have to be matched by content wherever they sit, not as one section.

- **Count matching paragraphs, not differing lines** (2026-11-06, headless retests). Counting differing lines penalizes a template that grew, so a brain that rewrote a paragraph fits an older, shorter template better. Subwiz's and lamarr's hooks, both seeded from 0.71, inferred 0.70 that way. Each then raised a false conflict over its deliberate clone path or name, and settling the conflict in the template's favor broke loading. Counting the copy's paragraphs a candidate holds word for word picked the right base on every file tested. The walk-through also keeps a brain's own values, such as its clone's name, in any template text it applies.
- **Newest on a tie misses additions and partial updates** (2026-11-07, PR #22 review). A paragraph a release only adds leaves the older template's count unchanged, so a 0.71 multi-lobe `CLAUDE.md` tied 0.71 and 0.72, took 0.72, and read 0.72's "A child works within its ancestors' choices" paragraph as the brain's deletion. A dream cycle with half of a release's changes applied by hand took the newer base and lost the other half. The bound and the fewest-unversioned tie-break fixed both, headless and by script.
- **A tie-break must count rewritten paragraphs as present.** Counting every template paragraph the copy lacks made 0.70 win for lamarr's hook, which holds 0.71's added worktree paragraph in rewritten form, and brought back last session's false conflict. Counting a paragraph as present when the copy holds a version of it at half or more word similarity restored lamarr's bases on every file.
- **The bounded rule found a fix the old rule missed.** Virtual-view-brain's three project hooks still read `../virtual-view-brain/` and "sibling clone", which is 0.70 text. The old rule took `HEAD` and reported nothing; the new one infers 0.70, recommends 0.71's worktree paragraph, and raises one conflict where the template rewrote the pull paragraph and the brain had filled its clone name.
- **An agent second-guesses an absent paragraph unless told not to.** With the declined paragraph left out by the merge, the headless second check read the brain's git history, saw the paragraph had never been there, called the omission a gap in check 10, and recommended it anyway. Check 10 now states that a paragraph the base and current template hold and the brain lacks is the brain's own, whatever its history, and a rerun reported nothing for it.
- **Inferring a base keeps breaking; a two-way comparison does not** (2026-11-07). Scripted against the real brains, the bounded base rule gave subwiz's hook a false conflict over its fixed clone path, the defect that broke its loading on 2026-11-06, and `git merge-file` joined a declined README change in lamarr with the brain's adjacent description line into a false conflict. The two-way comparison labels every case as a proposal: both review cases come out as one missing and four behind paragraphs, a declined lamarr README change returns as one behind paragraph, and a pristine 0.72 brain shows only behind and missing paragraphs, with no own edits.
- **A two-way comparison must leave out what `create` resolves.** The templates' staged comments, such as the hook's multi-lobe and maturity blocks, showed as missing in every brain that had resolved them; the brain's read-index and registry rows showed as own edits; and work setup's pointer to `templates/work/` showed as missing in every brain that inlines the scaffolds.
- **A report-only run still needs a temporary directory.** Told to change nothing, the agent fed the merge through pipes, which `git merge-file` misreads on macOS, and got false conflicts.

## Alternatives considered

- **Upgrade steps in release notes.** Left out of the 0.70–0.72 releases on Rob's call: it makes release notes load-bearing, and it reaches only owners who read every release in order.
- **A plain diff against the template.** Rejected: placeholders, maturity comments and legitimate adaptations make every brain differ, so a diff reports noise and can't say which differences matter.
- **A three-way merge against an inferred base.** Adopted on 2026-11-05 and replaced on 2026-11-07. It hid an owner's edits by treating the base-to-copy difference as the brain's own, but needed one release to stand for the file, which an edited file does not have. Every rule for choosing that release failed on some real brain, and `git merge-file` merges by line, not paragraph.
- **Per-file or brain-wide version stamps.** Rejected by Rob: an owner's edits mean a version does not identify a file's contents, and stamping made `check` a bookkeeper that rewrites every file.
- **Updating procedure files automatically.** Rejected: the toolkit's SCOPE puts migrating a knowledge store automatically out of scope, because the owner directs each change. Procedure files are part of the store's conventions, so the same holds.

## What this doesn't solve

- **Knowledge files written to an older standard.** A SCOPE seeded under a rule a later release changed is already `check`'s substance work, and stays there.
- **A brain that grew on its own.** Its procedure files were never copied from a template, so there is nothing to compare, and `check`'s principle scoring covers it as before.
- **An install without git history.** Nothing tells a behind paragraph from an own edit, so every changed paragraph is reported as an own edit.
- **Own edits and declined changes come back.** Nothing records a decision, so each `check` reports them again; that is intended, as a recurring review.
- **A multi-lobe brain's dream cycle.** It adapts the single-lobe template whole, so `check` skips the comparison and says so, until MULTI_LOBE_DREAM gives the template a multi-lobe story.
- **A toolkit installed outside the standard paths.** The dream cycle's release prompt finds no clone and says so in its log.
