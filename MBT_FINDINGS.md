# Mini-Brain Toolkit: Implementation Findings

> V26, 2026-11-09.

Findings made while building the toolkit that are not evident from reading the files themselves. Each entry names the options considered and the reason the chosen approach won. Assume the current files are available as ground truth — this document does not restate what they already show.

---

**The two procedure docs are named `CREATE_BRAIN` and `CHECK_BRAIN`, not `ESTABLISH` / `ASSESS`.** The names moved twice toward obviousness: from precise verbs (`ESTABLISH`/`ASSESS`) to plain verbs (`CREATE`/`CHECK`) to verb-plus-object (`CREATE_BRAIN`/`CHECK_BRAIN`). The driver each time: the audience is an agent scanning a read index for the obvious action, and naming both the action and its object ("create a brain", "check a brain") is what a user actually types — matching the index entry to that intent lowers the chance of the wrong doc being loaded. Precision lost to obviousness on purpose; the fuller framing survives in each doc's body.

**The toolkit must stand on its own as a canonical source: cite external prior art, strip internal lineage.** References to outside research — the agent-memory landscape, ADRs, related systems — are signal and belong in the research agenda. References to *which mini-brain a convention came from*, or to how this toolkit applies the pattern to itself, are redundant and uninteresting to a reader learning the pattern — and they are a live bleed vector: an early version of the research agenda carried domain-specific examples (a batch of security-vendor acquisitions) verbatim from a sibling brain used as its seed template, content with no bearing on the mini-brain pattern. The rule that follows: distill conventions from exemplar brains, then cut the provenance — the canonical reference and procedure docs state the pattern on its own terms, and any build-time lineage worth keeping lives here in FINDINGS, which exists for exactly that.

**The work-closeout edit classification was preserved when generalizing from its exemplar, not stripped.** `templates/WORK_CLOSEOUT.md` classifies each piece of knowledge before merging it, the load-bearing distinction being reconcile-supersede vs. append-log. The exemplar carried this with platform-specific examples that invited deletion during generalization; it was kept because the value lives in that distinction, not the examples. The transferable caution: when distilling a template from one brain, judge a convention by its mechanics, not by whether its illustrations are project-specific.

**"Work item" replaced "feature" as the unit of tracked work.** The setup/closeout bookends and the per-item working set were originally named for *features*, but the machinery (the target walk, the reconcile/append-log classification, the branch→PR→merge→fold lifecycle) is agnostic to whether the work is a feature, a bug fix, or a hardening effort. Naming it "feature" undersold that reach and invited a reader to skip the ritual for non-feature work. Renaming to "work item" (files `WORK_SETUP`/`WORK_CLOSEOUT`, slot `<WORK>`, dir `templates/work/`) widened the framing without changing the mechanics. Paired with the rename: setup now defaults to the **full scaffold** ("assume a branch and a PR until proven otherwise" — an oversized scaffold is cheap, under-scaffolding deep work is not), and closeout triggers on the work **concluding** (usually a merge, occasionally a no-code resolution) rather than strictly on merge.

**Commit conventions are deliberately not templated, and the project hook no longer mentions them.** Both living brains grew a commit-conventions section in their entrypoints, which reads from the outside like a template gap and was once proposed as one. It is an omission by design: how a repo commits is each brain's and each project's own choice, not one that is load-bearing for the mini-brain domain. The hook template first deferred to "the mini-brain's own commit conventions"; Rob had the phrase dropped, because even a deferral implies every brain should declare conventions, and prescribing commit policy to downstream brains costs adoption. The only commit and PR rules the toolkit carries govern this repo's own development. Living brains adding their own section is the system working, not template drift.

**Append-only was found to mean content integrity, not fixed position — no exception was carved.** Folding two logs into one during a restructuring looked blocked by the append-only rule: appending the retired log's entries after newer ones breaks chronology, interleaving them looked like a violation outright, and archiving is forbidden. The first response was to reject relaxing the rule, on the grounds that a migration-shaped exception weakens it for the common case to serve a rare one — sound reasoning, and unnecessary. The rule is stated in five places, and two of them already defined it as content integrity: an entry is never edited after the fact, and content above the new separator is never revised. Neither says anything about where a section may sit. Merging whole entries by date was therefore always legal, and only the bare phrase "append-only" suggested otherwise. Two alternatives lost to it: leaving the retired log in place as a closed sibling, which strands a document under a lobespace no lobe declares and makes every brain's checker carry a permanent exemption to serve a rare move; and folding it in as one summarized entry, which destroys the turn-by-turn lineage that session closeout exists to produce. Date merging also keeps the most recently written entry at the file's tail, which the read-from-the-last-separator ritual depends on. The rule that generalizes: when a standing rule appears to block a new move, read every place it is actually stated before carving an exception — the block may be an artifact of the rule's name rather than its content.

**Skills and roster-gated closeout are deliberately not templated in the project hook.** The exemplar narrowed its hook trigger to three phrases and that narrowing was ported to `templates/PROJECT_HOOK.md`; the two mechanisms it was narrowed *against* were not. In the exemplar those phrases are a fallback — typed skill commands and a session-start greeting carry discovery — and closeout eligibility is decided against a mirrored list of team contributors. Both were left out on the same grounds: skills are advanced, project-specific configuration a brain should not presume of its project repos, and an eligibility roster answers a question a single-user adopter does not have (who may push to a repo several people share) while reading like a mandatory setup step. What stands in for the roster is the trigger itself — the phrase that loads the brain is also the only thing that authorizes a closeout offer — so a seeded brain needs no identity configuration at all. Two alternatives lost: an escape hatch for an outright request ("or asks to load the brain") would soften the lost discoverability but reintroduces the fuzzy trigger the narrowing existed to remove; and an explicit no-skills prohibition in the create procedure was rejected as a rule against something that document never raises, since it complies by silence. The caution that generalizes: when porting a rule out of an exemplar carrying more machinery, work out what that machinery was compensating for before assuming the plain version stands without it — here the accepted cost is that a phrase nobody has taught the user is the only door.

**The scope and approach templates restate the create procedure's authoring rules in comments, on purpose.** Each section of the two templates carries a comment saying what belongs in it, deleted as the section is filled, and those comments repeat rules the procedure already states. The duplication is a deliberate exception to saying each fact once: the procedure is read once, at seed time, while the template is open at the moment the mistake gets made, so its copy is the one that prevents the error. A cleanup that deduplicates the templates against the procedure would delete the copy that works.

**Check commands enumerate files with `find` and anchored filters, never shell globs.** The namespace checks first globbed the markdown files in `working/`, and under zsh an unmatched glob aborts the pipeline, so on a brain whose `working/` was empty or missing the check printed nothing — which is its pass condition. An unanchored filter failed open too, accepting a lobespace that appeared anywhere in a filename. None of these commands had ever been executed when they were reviewed for merge, and the first run falsified three of them. The replacements tolerate a missing `working/`, anchor the lobespace to the filename's start, and were run against fixture brains, a planted stray included, before they shipped. The caution that generalizes: a check whose pass condition is empty output fails open on any error that also produces empty output, so verify it by executing its failure cases, not by reading it. (`c65245b`.)

**The check procedure fails stop when the target isn't a mini-brain, rather than handing off to creation.** An early design let a failed "is this a brain?" precondition pivot into the create procedure — a helpful-seeming handoff. It was rejected on safety grounds: asking to *check* a directory presumes a brain already lives there, so pivoting to *create* is a state-changing action that could overwrite or damage whatever is actually there, the more so under auto-approval. The rule that generalizes: a failed precondition in one procedure is a reason to stop, report, and let the user confirm the path or intent — never to invoke a second procedure that changes state. Dropping the handoff also removed the only cross-procedure reference, so no maintenance-doc boundary carve-out was needed.

**A document that admits a wrong reading is fixed by renaming it, not by rewording it.** The work-item checklist was renamed TASKS → BURNDOWN because two seeded brains had read TASKS in incompatible directions — one a master list restating the plan's implementation sequence, the other a summary of it — each consistent with what the file said about itself. Tightening the prose was the obvious cheaper fix and was rejected: a name appears in every reference to a document, its own filename included, and is read every time, while corrective prose is read once, so when the name and the instructions pull opposite ways the name wins. In ordinary usage a *task list* is everything outstanding — which is the master list — whereas a *burndown* is a quantity that goes to zero against a scope fixed when the item opened, so the writer's question shifts from "is this a thing to do?" to "must this happen before this ships?", and the second excludes the plan's contents by construction. The rule that generalizes: when a document's name fights its instructions, change the name.

**A young pattern forgets a discarded concept rather than carrying a rule to migrate away from it.** The rename first shipped with a setup rule that adopted legacy `*_TASKS.md` files by renaming them on sight; a review then found two edge cases in that rule, and instead of patching them the rule was deleted outright and TASKS was struck from the templates and procedures as both a name and a concept, kept only where its removal is recorded or taught. The reasoning: the pattern is too young to accumulate migration debt, only a handful of brains carry the old name, and a live TASKS concept — even one the toolkit knows only how to *retire* — is a standing attractor that re-invites the master-list drift the rename exists to kill. The migration rule was itself a place the discarded concept kept living. The few brains under the old name are each corrected by a one-time manual rename, so the toolkit needs no mechanism. The caution that generalizes: a rule to migrate away from a concept keeps that concept alive; for a pattern still small enough to fix its instances by hand, forgetting beats deprecating.

**A model-executed instruction fails when its load-bearing rule sits in definitional prose; the fix is an imperative at the decision point.** `templates/WORK_SETUP.md` intended lobespace-prefixed work-item filenames from the start, but stated the prepend rule only inside its slug step's prefix-distinctness discussion — so setup runs skipped it and sometimes emitted a bare, unprefixed slug. The templates are instructions a model executes, not documentation a human reads, so the executable form outranks a definition-led opening: the slug paragraph now leads with the imperative (every produced filename is `<LOBESPACE>_<WORK>_*`; derive the slug from the work-item name; lead with the owning lobe's lobespace) and resolves the handed-name ambiguity by input shape before any definition. PR #3. The placement is pinned deliberately because it is fragile — the same paragraph was silently re-demoted to a definition-led opening in an unlogged session and had to be restored on review, a regression invisible sentence-by-sentence and caught only by re-checking the final text against the item's root-cause diagnosis and its manual test cases. The caution that generalizes: when a template instruction is model-executed, the position of its commanding sentence is load-bearing, and a later wording pass that reads well locally can still move it back into definitional framing and reopen the failure.

**The work-item lobespace prefix is knowingly redundant with its directory but was kept, because removing it is not confined.** Enforcing the prefix in `templates/WORK_SETUP.md` sharpened a single file; dropping the lobespace from working filenames would touch the `<LOBESPACE>_<WORK>_*` glob threaded through the setup, closeout, session-closeout, and project-hook templates, and would puncture two invariants — the universal-lobespace naming law and the longest-match ownership cross-check that catches misfiled work files in multi-lobe brains — while the scannability payoff lands mainly in single-lobe brains. So the redundancy stands. Retiring it pattern-wide — making the directory the sole ownership signal — is deferred to its own redesign, not folded into a fix meant to confine itself to one instruction. PR #3.

**A move to `archive/` never overwrites, and on a collision the incoming item takes the new slug.** Work setup stopped reading `archive/`, so a slug can be reused, and a retiring file could then silently replace an archived one of the same name. The rule sits in the entrypoint's `working/` convention rather than in work closeout's retire step, because work closeout reads the entrypoint first and the convention also covers early plan archival, which the retire step does not. The incoming file is renamed, not the archived one, so log entries that name the archived file still reach it. The item's whole set is renamed and its internal references rewritten before any move, because renaming only the colliding file leaves its siblings citing a name that now belongs to the older item. (PR #20.)

**The pattern's core terms were renamed because enforcement cannot solve a collision with ubiquitous vocabulary.** "Unit," "token," and "component" each carry precise meanings in the pattern while sharing names with ordinary software concepts (unit test, auth token, software component). A grep-based enforced-terms entry for any of the three generates overwhelmingly legitimate ordinary-English hits, burying real collisions in noise — the mechanism fails its own selection criterion. The replacements — "lobe" (extending the brain metaphor: distinct functional regions) and "lobespace" (a self-describing compound of lobe + namespace) — collapse three collision-prone terms to two collision-free ones. Alternatives rejected: enforcing the current terms (too many false positives), "prefix" for token (still collides with CSS/CLI prefixes), "cortex" for unit (maps poorly to nested structures — a sub-lobe is not a sub-cortex), and invented opaque terms (zero collision risk but zero etymological help). PR #5.

**A placeholder's name can carry a binding time, and collapsing names collapses that too.** The vocabulary rename unified two template placeholders (`<PREFIX>` and `<TOKEN>`) into `<LOBESPACE>`, which looked like pure vocabulary work because both denoted a lobespace. What distinguished them was *when* they resolve: one was substituted once when a brain is created, the other stays a runtime variable resolved per owning lobe and work item. With a single name, the work-setup and work-closeout templates pointed multi-lobe brains at maintenance documents that cannot exist under a child's lobespace — the multi-lobe layer says session closeout, work setup, work closeout and the dream cycle live only at the hub. The fix introduced `<HUB>` for the creation-time, hub-only sites and kept `<LOBESPACE>` as the runtime per-lobe variable, restoring a name-based substitution rule that is decidable over the template set. The positional rule it replaced ("hub docs vs. doctype grammar") was undecidable: the multi-lobe entrypoint's doctype grammar is a file-set table that has to stay runtime, but the positional rule classified all file-set tables as creation-time. PR #5.

**Enforced terms are a disambiguation list, not a glossary.** Each document is written without its siblings in view, so a word with a precise meaning in one is picked up as an ordinary generic in another, and the collision shows only when both land in one context. The by-eye one-term-one-meaning check was not enough on its own: asserting a candidate list against this brain found several words already carrying two senses. What no document holds is that a word is *taken* and which sense it will be mistaken for, so an entry's load-bearing part is its disambiguation. Four alternatives lost. A glossary defines the whole vocabulary, grows without bound, duplicates each term's home document, and warns the reader rather than the writer about to repurpose a word. A disambiguating qualifier stays the usual fix but lost as the mechanism, because nothing records which words need one. Per-document declarations put the reservation where the term is already used correctly, not where it gets misused. A section in the entrypoint's conventions would load the terms into every session, while a standalone file with a read-index row and a one-line write-time rule enforces the same thing at lower cost. The known limit: an entry enforces a word against a rival meaning, never a concept against a rival word, so a brain that calls one thing by two names gets no signal from it. PR #7.

**The enforcement hooks were cut back to what the first adopting brain runs.** The first build hooked every point where a term could be touched, including two that a product brain already using enforced terms does without. A callout for terms a work item coins, recorded for closeout to act on, was dropped because nothing downstream reliably consumed it; closeout checks the docs it edited for conformance instead, and proposing new terms is left to the dream cycle. The dream cycle's term check moved out of its mechanical structural phase into a judgment phase of its own, because every hit needs a call about which sense is meant, and an unscoped grep reaches the append-only logs, whose hits can never be fixed. The adopting brain's session-closeout terms rule was not copied, because the entrypoint's write-time rule already covers log entries. The caution that generalizes: when a mechanism has a working adopter, ship the hooks that adopter runs, and make any extra hook name its consumer before it earns a place. PR #7.

**Procedure documents stay in the term check's scope.** Procedures use everyday verbs that collide with listed terms, which invited exempting them. Rob decided against it: the dream cycle's drift pass and work closeout's terminology check already cover procedures, so exempting them in the check alone would give three verdicts on one brain, and this brain's Finding entry exists mostly to keep procedures from using the word generically. Such a collision is an entry concern instead — it shows the entry's disambiguation fails to rule out that sense, and the brain decides whether to reword the procedure or widen the entry. PR #7.

**The flat platform split was struck rather than reconciled with the lobespace rule.** The convention put a platform qualifier ahead of the lobespace (`<PLATFORM>_<LOBESPACE>_*`), where every naming check and the lobe-ownership rule expect the lobespace, so a brain following it failed its own checker. Moving the qualifier behind the lobespace would have fixed the checks but kept a second way to divide a brain's documents beside the multi-lobe layer, with no template, check or maintenance pass of its own. Its migration row went with it, since only one brain used the convention.

**SCOPE and APPROACH divide by premises and a second approach, and the test is negative.** The first neutrality test asked whether a claim would still hold had the design gone another way, which a fact about the chosen platform always passes, so a seeded scope could catalogue its platform's internals and still read as neutral. What catches it is relevance: a sentence only the intended design needs is a choice. The positive form, keeping only what the second approach also needs, was rejected after a blind re-author used it to push a condition most alternatives face out of a real scope; one review round later restored it by accident, and it was removed again. Blind readers of the same scope disagreed until the check made them settle the premises and the second approach with the owner first, and converged after. (PR #18, `34ccd69`.)

**Rejected ways to keep the design out of SCOPE.** A Platform section in APPROACH was rejected by Rob, because not every project is a platform; APPROACH states what the design builds on instead. Renaming the section "State of the Market" misfits an internal library, and the content rule does the work. Forbidding platform facts outright fails because some bind every approach and are part of the problem. Requiring the second approach to meet every goal fails because goals exist to rule approaches out. Leaving market figures outside the status test was rejected because alternatives are described by what they require and how they charge, and a figure kept is dated. (PR #18, `34ccd69`.)

**Alternatives may be partial, and lobes align top-down.** An alternative was first defined as something adoptable for the whole problem, and a child lobe took a parent's choice as given only when the parent's own goals needed it. A dry run against four brains, one by an outside author, found both misfiring on owner-approved scopes: partial options that state where they fall short are the ones a project exists to beat, and a parent choice made for a reason outside any goal fit neither branch of the qualifier. Rob replaced both with principles. An alternative is the next-best option, assessed for where it falls short, and a child works within its ancestors' SCOPE and APPROACH, revised when they change. (PR #18, `34ccd69`.)

**Unattended dream cycles verify only the systems in reach.** Widening maintenance to every kind of SCOPE claim would stop an unattended cycle on claims about alternatives and evidence that nothing can verify, or add web agents and a rotation to every brain's cycle. Those claims are verified when a person is present, at create and check, and an unattended cycle lists them as unverified. (PR #18, `34ccd69`.)

**The toolkit installs as a skill whose root is the repository.** A `SKILL.md` at the repo root makes a clone placed in a harness's skills directory the skill itself, so install is a `git clone` and update is the README's install line. Three packagings lost. A plugin would install and update through `/plugin` and give each command its own menu entry, but plugin skills are namespaced, so the commands would read `/mini-brain-toolkit:create`; that namespacing was not verified against current Claude Code docs, so it is the claim to recheck if per-command menu entries come to matter. A `skill/` subdirectory as the skill root would make every procedure path resolve one level up, and the clone could no longer be installed directly into a skills directory. A prompt asking the agent to install from the repo URL would still have to state what the URL can't (the whole repo is the skill, it is a git clone, it installs per user), and a wrong install would surface only when the command first failed in a new session. `SKILL.md`'s path rule supplies the toolkit root the procedures assume, so they needed no edit. The rule covers only `MBT_*.md` files and `templates/`, because the procedures also name the target brain's files, such as its `CLAUDE.md`, which would otherwise resolve into the install. `disable-model-invocation` stays on because create and check are always started by the user, and an auto-invoked skill would compete with the project hook's trigger phrases. (PRs #17 and #19.)

**The README's install line is one pasteable line that installs or updates to the newest release.** A README command is copied rather than read, so it is judged by whether it pastes as one line and whether it reruns cleanly. The line tests for the directory with `if` rather than chaining `fetch || clone`, because a failed fetch would fall through to a clone that fails on the existing directory with a misleading error. Only a successful fetch or clone leads to the checkout, so an unreachable remote exits with its error rather than checking out a stale tag. It then checks out the newest release tag by version order, so users run only released code, and a brain's dream cycle can tell a newer published release from a commit merged to `main`. An install someone has edited keeps its uncommitted edits, because the checkout carries them over or refuses to overwrite them. A local commit stays only on the branch it was made on, and the checkout drops it from the working tree. A shallow clone was rejected: the packed repo is about 344 KB, and `check` reads earlier template versions out of the full history. A release-candidate tag would break the line, because git's default version order ranks `0.73-rc1` above `0.73`. (PRs #17, #22 and #24.)

**Every README section gives each harness its own command, and Other harnesses comes last.** Install, create and check each open with a paragraph describing the step, then a heading per harness carrying the exact command, so a reader never rewrites one; a note telling the reader to adapt a command was removed rather than placed better. Other harnesses is last in every section, so a harness added later is a block inserted before it. It is not headed "Without installing", because it still installs a clone at a fixed path. OpenCode 2's instruction to pick the skill from the `@` menu sits in the create and check labels rather than once after the install blocks: a typed or pasted `@mini-brain-toolkit` reaches the model as plain text and silently fails, a reader copies a command without rereading install, and a reader of check may not have read create. A harness gets its own block only once the brains create produces load in it, which is why Codex and OpenCode 2 waited for the hook to move to `AGENTS.md`. (PRs #17 and #19.)

**The install blocks and the closeout rest on harness facts that change between versions.** These were verified on 2026-11-03 in Claude Code 2.1.318, Codex 0.166.0 and OpenCode 2.2.5; recheck them against the installed version before changing an install block, because OpenCode's main docs still described version 1 when version 2 had changed invocation, auto-invocation and duplicate handling. Codex and OpenCode 2 install into `~/.agents/skills`, the one directory both read. OpenCode 2 also reads `~/.claude/skills` and resolves a duplicate by folder name, with `~/.agents/skills` registering later and winning, so a user with both installs gets the copy the README assigns OpenCode 2. Codex ignores `disable-model-invocation`, so `agents/openai.yaml` sets `allow_implicit_invocation: false` to keep the skill from competing with the hook's trigger phrases in `AGENTS.md`. OpenCode 2 has no `CLAUDE.md` fallback, and Claude Code reads `AGENTS.md` only when no `CLAUDE.md` exists, which is why a project's `CLAUDE.md` imports the hook rather than relying on either file alone. OpenCode 2's read tool does not expand `~`, so the Other harnesses prompt's path relies on the harness expanding it. The closeout reads only the running harness's session ID variable because a harness started from another's session inherits that one's variable; the transcript-location lookup it replaced cannot work in OpenCode 2, which keeps sessions in SQLite. OpenCode 1 is not supported, because it has no user invocation of skills. (PR #19.)

**The brain entrypoint stays `CLAUDE.md`, and a one-line `AGENTS.md` sends other agents to it.** Renaming the entrypoint to `AGENTS.md` would touch the pattern, the lobe layout and every template, all of which name `CLAUDE.md`. The project hook was not also written into the project repo's `CLAUDE.md`, because that leaves two copies to keep in sync. Check's loading-reach fix also adds `AGENTS.md` to the target brain's exemptions and to its dream cycle's exclusions: in review, adding the file alone made the next check and the brain's own dream cycle flag the file the fix had just added, up to five issues from following check's advice. A fix that adds a file must update everything that checks files. (PR #19, `0bd87bf`.)

**`SKILL.md` forbids writes under the install rather than special-casing a copy of the toolkit.** A copy of the toolkit is the one target that shares the `MBT` lobespace, so the path rule sends its `MBT_*.md` reads to the install, where approved fixes could also land. A rule resolving every path against the target when it is a toolkit copy was built and tested first. Rob rejected it because it frames maintaining a copy of the toolkit as an expected workflow; the toolkit maintains itself through its dream cycle. One fail-closed sentence keeps any target from editing the install without endorsing that case. In Codex and OpenCode 2, a control without the guard also fixed only the copy, so the guard is a backstop rather than a fix. (PR #19.)

**The release pin shipped apart from the drift check.** A pinned line checks out the newest tag, so merging the pin before a tag existed at or after the drift check's merge would have rolled any install updated in between back to the previous release. Rob split the pin into its own PR rather than cut a release to make one merge safe. In the end the pin merged hours ahead of the 0.73 tag, so the acceptance run could test it. The template dream cycle's release check moved with it, because it never fires on an install that tracks `main`. (PRs #22 and #24.)

**Check finds procedure drift by comparing each file with the current template, after version stamps and a three-way merge were each built and removed.** The first design built was a three-way merge from a stamp in each procedure file naming the template version it was copied from. Rob rejected every form of stamp, per file or one for the brain: an owner may edit a procedure file for their own purpose, and once they have, no version says what the file holds. Stamping also turned check from a reader into a bookkeeper that rewrites every file it checks. The base was then inferred from the file's text, and the merge failed on the same fact, since it needs one release to stand for the whole file. Each rule for choosing that release broke on a real brain or on a case from review. Counting differing lines favored an older, shorter template once a paragraph had been rewritten. Taking the newest release on a tie read a release's added paragraph as the brain's deletion, and lost the untaken half of an update applied by hand. Bounding the base by dropped text misjudged a hook whose rewrite was too short to count as a version. `git merge-file` merges by line, so it also joined a declined change and an adjacent own line into one conflict. A false conflict is not harmless: in a test that settled every conflict for the template, one overwrote a scratch copy's fixed clone path, which would have broken that brain's loading. The two-way comparison labels each paragraph on its own from the template's history, so no version stands for the file and every difference stays a proposal. A declined change and an own edit come back on every check, which Rob wants as a recurring review. The accepted cost is that an install without git history, or a shallow one, shows every changed paragraph as an own edit. The caution that generalizes: when a rule keeps needing tie-breaks, question what it is choosing between. (PR #22.)

**The drift comparison normalizes placeholders and leaves out what create resolves.** Real brains fill placeholders inconsistently: one keeps `<LOBESPACE>` where it names the owning lobe at runtime and another fills it in, and comparing one brain's work closeout without normalizing raised twelve false differences. Check fills each template version's creation-time placeholders with the brain's values and leaves runtime placeholders alone, so an untouched copy matches its source. In a single-lobe brain it also reads the brain's lobespace and `<LOBESPACE>` as the same in every text, because a brain may keep the placeholder in one slot and fill it in another. The cost is that a placeholder left unfilled by mistake compares as current. The templates' staged comments, the read-index and registry rows, and work setup's pointer to its scaffolds are all resolved or filled by create, and each showed as drift in each brain that had resolved it until it was left out. Brains inline work setup's scaffolds under at least three heading shapes, so they are split out by content. Earlier template versions are read from every commit that changed a template, not only from releases, because installs tracked `main` before the pin, and a brain seeded between tags would show toolkit text as its own edits. (PR #22.)

**Check labels each drift paragraph from the template's versions as read, never from a search of its history.** A headless check of an example brain labelled a hook paragraph behind after `git log -S` found a commit containing part of its sentence. The paragraph matches none of the five versions the template has held, so it is an own edit, and a rerun that read every version labelled it so. A history search finds a commit that touched a string, not a version that held a paragraph, and the mislabel turns an owner's edit into a recommendation to replace it. The same run showed a limit of grading by labels: the agent normalized placeholders the reverse of what check then said, its labels matched the grader's anyway, and only the transcript showed the wording had not been followed. A test of a procedure's wording therefore reads the transcript for whether the wording was followed, not only the result. (`76cd371`.)

**Rejected ways to bring an existing brain's procedure files current.** Upgrade steps in release notes make the notes load-bearing, reach only owners who read every release in order, and say nothing to a brain several releases behind. A plain diff against the template reports noise, because placeholders, maturity comments and legitimate adaptations make every brain differ. Updating the files automatically was rejected because procedure files are part of a knowledge store's conventions, and the owner directs each change to those. (PR #22.)

**The acceptance battery fits whatever machine runs it, and keeps no results.** Rob rejected a full matrix of harnesses, shells and brains as a definition of done: no maintainer's machine has every harness and example brain, and a contributor's won't either. He rejected recording each release's results because a record nobody audits only adds work. The cost is that a regression between two runs is caught only by a scenario that fails, never by a changed result. A golden machine with every harness and example is deferred rather than rejected, and the battery does not wait for it. Leaving tests to each work item, as before, lost because an item's fixtures and grading scripts retire with its working docs, so nothing repeats between releases and a fixed defect can return unnoticed. (PR #25.)

**The commit under test installs under its own skill name, not under a scratch `HOME`.** A scratch `HOME` was tried first, and Claude Code reported itself not logged in, because its sign-in lives with the real `HOME`. Rob chose the test name over a long-lived token or a sign-in for each run, since it leaves every harness's sign-in alone. Copying over the runner's install and restoring it afterwards was rejected because an interrupted run leaves that install broken. (PR #25.)

**The drift grader ships in `tests/` and reimplements check's comparison.** Without a script, a tested agent's drift labels could be judged only by another agent. Keeping the script in `archive/` lost on two rules: the acceptance recipe would cite an archived file, and the dream cycle's leakage check would try to inline the script into the doc that cites it. A hidden `.tests` would need the same allowances as `tests/`, since the path written in the recipe triggers the dream cycle's cross-reference check, and it would hide the grader from `ls` and search tools. The cost of a second implementation is coupling: a change to check's labels or exclusions that leaves the script alone fails every drift scenario on the mismatch, so the two change together. A change to the grader is verified by running it on every example brain before and after and comparing the two runs, because a fix that passed its targeted test regressed a real brain. (PR #25.)

The dream cycle's leakage exemption had no scenario either, and never reproduced, since the control flagged the planted `working/` citation too, so that scenario is unproven as a catch. The second-machine run added that a scenario's prompt is part of the scenario: until scenario 6's was pinned, a failure could not be told apart from the wording. The caution that generalizes: name the scenario that should catch a defect before reintroducing it. (PR #25.)
