# Mini-Brain Toolkit: Check an Existing Mini-Brain

> V37, 2026-10-30.

This document is the procedure for evaluating an existing mini-brain against the pattern and surfacing where it could improve — whether the brain was built from this toolkit or grew on its own.

**Stance.** This is a diagnostic that produces *opportunities*, not a grade. Most repos match some principles and not others; partial adherence is normal and fine. A repo can be a healthy mini-brain without doing everything here, and doing everything mechanically without the underlying value misses the point. Lead with what's working, then what would help most. A check is a conversation with the user who asked for it: put judgment calls to them as they arise, and change the target only where they direct.

**Inputs.** The path to the target repo. If the user hasn't named it, ask. If a known healthy mini-brain is available to consult, use it to calibrate what "good" looks like for a convention before judging the target against it — but the pattern reference (`MBT_PATTERN.md`) is the authority, not any single exemplar.

---

## 1. Orient

Read the target's entrypoint first (`CLAUDE.md` or equivalent), then list the repo top-level and its `archive/`/`working/` dirs. Identify: the lobespace in use, which canonical docs exist, whether there's a session log, and what stage the brain is at (per `MBT_PATTERN.md`: seed / content / mature). Read the canonical docs' first lines (not their full bodies yet) to see version headers and purpose. This is a bounded, low-context pass — save heavy full-file reads for §3.

**If the entrypoint carries a lobe registry**, the brain uses the multi-lobe layer described in `MBT_LOBES.md`. Note the hub lobespace and every lobe's directory and lobespace, and list each lobe's directory rather than the top level alone. Several checks below then run per lobe instead of once. A brain with no registry is single-lobe and everything runs as written.

If the repo has no entrypoint and no namespaced docs, it may not be a mini-brain — or the path may be wrong. Say so and stop: report that the target doesn't look like a mini-brain, ask the user to confirm the location, and do nothing else — don't score it, and don't scaffold what's missing.

---

## 2. Score against the principles

Walk the ten principles from `MBT_PATTERN.md` one at a time, in order. For each, give a verdict — **present / partial / absent / not applicable** — with a one-line note on what you actually saw, and (when not present) the concrete opportunity. The table below is a checking aid, not the authority.

| # | Principle | What to look for |
|---|---|---|
| 1 | Keep only what can't be re-derived | Docs hold *why*, not a restated copy of the code/README. Is there a stated bias toward small? Contrast: a store that mirrors the architecture and only grows. |
| 2 | Its own repository, outside the code | The brain is a standalone repo beside the project repos, not a folder committed inside one. Contrast: docs forked and versioned with the code they describe. |
| 3 | Orthogonal documents | Each doc covers one non-overlapping dimension (problem, approach, findings, log); a question maps to one file. Contrast: overlapping docs, or one doc covering everything. |
| 4 | Log separate from distilled docs | An append-only, dated, attributed session log *and* a distinct set of living current-state docs. Contrast: one mutable blob, or an ever-growing log never distilled. |
| 5 | Entrypoint with read index | One file a reader opens first, carrying a table of what to read for a given question and what's current vs. retired. Contrast: locating files by guesswork. |
| 6 | SCREAMING_SNAKE_CASE namespace | A shared uppercase lobespace on every knowledge file; wouldn't clash if two brains loaded together. Contrast: generic names lost among repo files. |
| 7 | Versioned and dated | A lightweight `> V<N>, date` stamp on canonical docs; history left to version control. Contrast: undated docs, or in-tree "old version" copies. |
| 8 | WIP apart from settled | A `working/` (or equivalent) holding area for drafts/experiments, distinct from the trusted core. Contrast: provisional and canonical content mixed. |
| 9 | Standard open/close of a work item | A setup ritual and a matching closeout that harvests durable lessons into canonical docs and retires (moves, not deletes) scratch files. Contrast: every effort reinventing structure and stranding its insights. |
| 10 | Scheduled reflection pass | A defined, recurring review of the *memory itself* that both prunes re-derivable content and looks for gaps. Contrast: a store only ever added to. |

Principles 9 and 10 are stage-3 machinery — mark them **not applicable** (not **absent**) for a seed or content-stage brain that legitimately doesn't need them yet. The signal is need, not a checkbox: a brain tracking many work items with no closeout ritual is a real gap; a small single-purpose brain without one is fine.

Score a multi-lobe brain's principles 5 and 6 against the multi-lobe layer, not against enumeration. Principle 5 is satisfied when a hub index, a doctype grammar and a registry together resolve every document — not when every document is listed. Principle 6 is satisfied by a lobespace declared per lobe, not by one lobespace across the brain.

---

## 3. Verify substance, not just structure

Structure can be present while the content rots. Spot-check the things that decay silently — delegate the read-heavy parts to Explore agents so the active context stays free for judgment. Five checks are the exception, run by whoever is judging and never split across agents. An unlisted term collision, a duplicated question and a parent's overreach are each invisible to a reader holding one document. The design and approach checks read SCOPE against APPROACH and, in a child lobe, against the parent, and the design check settles its test in conversation with the user.

- **SCOPE factual drift.** Pull a handful of falsifiable claims from the scope doc about the alternatives it assesses, the systems the problem holder works within (their structure, their gaps, and especially *absence* claims like "no control does X"), and its evidence, and check each against what it describes. Absence claims break silently when capabilities are added — prioritize them. Report claims that no longer hold. Claims about alternatives and evidence need current published sources, so check them in the active context with web access, never through an Explore agent. Skip identifiers, settings and counts that a system's own code is the source of; they are re-derivable content, never corrected.
- **Status check: SCOPE or APPROACH drifted into status.** Read every section of SCOPE and of APPROACH for the project's own progress. Status belongs in neither.
  - **What counts.** The project is what this brain's work builds; a system it serves is part of the world, even one the same organization makes. A scope describes the problem as whoever has it would meet it without this project, so the status quo is what they would have without it, and what the project has shipped, an earlier phase included, is status however much a later phase builds on it.
  - **Where it hides.** Status most often fills a section headed "State of the Problem", "Current State" or similar. It also hides in a status line opening a goal, a resolution recorded under an open question, a roadmap note saying when the project will do something, and a clause that dates the scope to the project's progress: "not yet", a "today" that marks the project's progress rather than the world's, or the problem's origin told in the past tense.
  - **The tells.** Version numbers, test counts, release status, maturity labels, benchmarks, issue counts, issue and commit references, and decision dates, when they describe the project.
  - **Not status.** Another product's release, a platform's requirement, a qualifier on the strength of the scope's own evidence (even one worded as "so far"), and the date that evidence was read. A mark in APPROACH that a goal is unmet is not status either, so long as it says what is unmet rather than when that will change.
  - **Remedies.** Report status as a deletion, splitting a passage that mixes it with a fact about the world, except in these cases:
    - A dating clause or a past-tense origin is a rewrite that restates the problem's structure in the present tense, which stays true after the project ships.
    - Status that carries the evidence a decision rests on is restated, without the status, as that decision's rationale in APPROACH, moving there when it sits in SCOPE.
    - Status that carries a lesson the approach does not rest on is a move to FINDINGS, stated without the status.
    - A resolution that records a design decision APPROACH lacks is a move to APPROACH.
    - A decision in APPROACH worded as status, such as "no cookbook exists", is a rewrite as the decision it records.
    - A whole section or subsection that has drifted was never gathered, so it is a rewrite rather than a trim.
  - **A declared convention.** A scope that declares status part of its job, in its header, its goals or a section's own introduction, follows a convention its brain chose. Put that convention to the user first, saying that keeping it exempts only the status and that the design check still reads those passages. Report its passages only if the user retires it.
  - **Headings.** The heading itself is cosmetic: "Current State" invites the drift and is worth renaming when the section is next touched, but a section under that name whose content is right is not a defect.
- **Parent overreach** (multi-lobe brains). A parent names what a child elaborates and stops. Where a parent explains *why* a child's problem is hard, or how it is solved, in its own words, that explanation belongs to the child — the tell is a passage equally at home in either document. A parent's APPROACH that decides a child's internals overreaches the same way.
- **Design check: SCOPE drifted into design.** A scope can be current and accurate and still carry the intended design's choices. Run this check after the status check, skipping the clauses that check reported, in three steps:
  1. **Settle the test with the user.** Read the scope through once, then settle three things.
     - **Premises.** List the premises the scope takes as given anywhere in it, such as a platform, a model, an audience or a pattern, and ask the user which belong to the problem holder (whoever has the problem the scope states) and which to the design. A goal asking for something the problem holder already has does not make that thing a premise; only the user's answer does. Each premise the user keeps names what makes it binding, such as a system every approach must work within or a commitment the problem holder made outside this project; a preference with nothing binding it is a choice, or a goal when it concerns an outcome, even when the user is the problem holder. A frame resting on a premise the user kept is not an issue.
     - **A child lobe's premises.** They include the ancestors' design choices the child works within, as `MBT_LOBES.md` describes. A parent choice the parent overreach check reported is still given to the child until the parent is corrected. Report one the child's problem depends on without naming it in its problem statement as an addition, and one named that no longer matches the parent's choice as a rewrite.
     - **The second approach.** Propose one and confirm it: the reasonable alternative to the whole intended design that differs from it most while honoring the premises the user kept. Gather candidates from the alternatives the scope assesses that replace the whole design, those APPROACH weighs, and any reasonable one assembled for the purpose, then take the one that differs most; the status quo serves only when no other alternative exists. Read a design built in phases whole, its shipped phases included. In a child lobe, the second approach replaces the child's design within the choices the child takes as given.
  2. **Read every section as the second approach's designer.** A passage that only the intended design needs is a choice; one the second approach needs in another form is a frame to rewrite neutrally. The cases below are where this most often shows, not the whole test.
     - A fact about an environment only the intended design uses, such as a platform's internals, or something the problem holder has that the problem does not require every approach to use. A system the problem holder requires every approach to work within is part of the problem, but only at the depth the problem needs: identifiers, settings and counts that system's own code is the source of are re-derivable content, reported as a deletion. A fact the world publishes, such as a standard's limits, stays even where the project's data encodes it.
     - A boundary or a narrowing of who has the problem that gives no reason, or justifies itself by what the design can reach, test or support. In a multi-lobe brain, judge a boundary in the lobe that sets it; a child relying on an ancestor's boundary or choice takes it as given, as `MBT_LOBES.md` describes.
     - A problem statement framed by its answer, which hides the choice of that answer.
     - A design rule stated as a fact about the world, such as what the solution "has to" do.
     - A goal stated in the intended design's terms, naming its mechanism, an artifact or the project, so that no other design could be judged against it. A goal the second approach fails because it would leave the problem holder worse off is not an issue, since ruling approaches out is what goals are for; one it fails only because it does the work another way is.
     - An open question that offers design options, presupposes the design, or asks whether the design will hold.
  3. **Read what remains for sufficiency.**
     - **Alternatives.** A state of the problem leads with the alternatives: the status quo, doing it by hand where that differs from the status quo, those a reasonable person would weigh beside them, and the intended design's own class, described generically by what it requires. An alternative is any option someone with the problem could take instead, even one that covers only part of it, assessed for where it falls short. In a child lobe, the alternatives are those to the child's own part within its parent's choices; where those choices leave none beyond the status quo, the status quo, the conditions and the evidence suffice. A section that buries the alternatives needs reordering. One that omits the status quo, a distinct by-hand option, or the intended design's class, assesses only the status quo, or states conditions and evidence but assesses no alternative needs what is missing added. One that gives no evidence that the problem is real needs that added too.
     - **Never gathered.** A scope with no such section, and one with no goals, were never gathered, so report that section as a rewrite rather than listing what it lacks, unless the status check already reported it. Where the section holds status under a convention the user kept, report a state of the problem to add beside it instead.
     - **Gaps.** Check whatever goals there are against the gaps the scope shows. A gap is where an alternative stops or a condition every option faces bites; an alternative ruled out by a premise leaves no gap. Each goal answers the problem statement or a gap, and each gap has a goal, an exclusion or an open question; report a goal with no gap, and a gap with no home, for the user to resolve.

  Report each issue with one remedy; where a passage is split, each part is an issue with its own.
  - **Delete** what APPROACH already holds as a decision, and what the code already shows. A passage APPROACH holds only as status is not held.
  - **Relocate** within SCOPE a consequence the problem needs when its passage is deleted or moved, to the section it belongs in.
  - **Move** to APPROACH what only the design needs and APPROACH lacks; where APPROACH holds part of a passage, delete that part and move the rest. In a multi-lobe brain, a move names the lobe whose document receives it.
  - **Rewrite** a frame that hides a choice, or a boundary whose reason in the problem is evident, splitting a passage that mixes the problem with the design so each part takes its own remedy.
  - **Reorder** or **add** where sufficiency fails.
  - **Leave to the user** what only the problem holder can settle, such as a boundary whose reason only they know.

  A remedy that changes a passage APPROACH cites, such as a goal's name, names the citing passages. Where issues cover most of a section, report that section once as a rewrite, naming what it must carry, rather than passage by passage; where most sections need that, report the scope once as one to re-gather, naming what each section must carry.
- **Approach check: APPROACH against its SCOPE.** Run it once the design check has settled the test, against SCOPE as the design check's remedies would leave it. APPROACH states, wherever it places them, whom the design serves, where that is narrower than whoever has the problem, and what it builds on beyond SCOPE's premises, which it honors without restating them as its own choices. It argues against the alternatives SCOPE assesses and names the settled second approach as such. Every goal has an answering decision, and a goal the design leaves wholly or partly unmet is marked. Report what is missing as an addition to APPROACH, and a premise restated as a choice as a rewrite; a settled second approach APPROACH does not name is added, so the next check finds it. In a child lobe, APPROACH works within its ancestors' approaches.
- **Re-derivable content.** Skim the canonical docs for passages that merely restate what the current code plainly shows. Skip SCOPE passages the design check already reported. These are pruning candidates (principle 1) — the brain would be *more* trustworthy smaller.
- **One term, one meaning.** Read the brain's top-level documents, never its logs or `archive/`. *Listed terms:* for each term the brain's enforced terms file lists, grep its stem so every inflection matches ("authenticat", not "Authentication"), and judge each hit against the entry's enforced sense and its disambiguation. Look hardest at the senses the entry rules out and at the word's meaning in adjacent vocabularies (a protocol's, a cloud provider's), where misuse concentrates. Report a misuse as a wording fix. Report a use showing the entry itself is wrong or too narrow as an entry concern, with the evidence. *Unlisted terms:* read the top-level documents as a set and watch for a loose synonym standing in for a listed term, reported as a wording fix, and for a word carrying two jobs (a domain term in one document borrowed as a generic in another); each reading is defensible alone and the collision shows only side by side. Report a collision as a candidate enforced term for the user to confirm only when it meets the enforced terms file's own rule for adding an entry, or the rules in `templates/ENFORCED_TERMS.md` when the brain has no such file. *The file itself:* check the enforced terms file against its own stated rules and entry format, and report an entry with no disambiguation as needing one when its term was misused, or as a retirement candidate when it was not.
- **Question ownership** (multi-lobe brains). An open question belongs to exactly one lobe: the one whose work would resolve it. The same question standing in a parent and a child means neither owns it, and the copies drift as the answer develops.
- **Shape.** Ask of each lobe whether its SCOPE still states one problem, or whether writing it honestly today would force two onto the page. A brain that should have split is internally consistent either way, so no structural check can see it; the tell is a lobe that authored one target's documents first and ported a second against them.

Also run the structural checks below; they're mechanical and catch the cheap, common failures.

### Structural checks

1. **Read index ↔ disk** — every file in the read index exists; no top-level knowledge file is missing from the index (orphans). Ignore HTML-commented entries (`<!-- ... -->`) — a brain commonly stages its read index with commented-out rows for docs it will add later. *Multi-lobe brain:* run that against the hub index and the hub's documents, then check the registry against disk both ways — every registered lobe has a directory, every lobe directory is registered, at every depth — and check grammar conformance: every lobe carries the full doctype set, and any document beyond it appears in that lobe's **Also holds** cell or its local index.
2. **Version headers** — every canonical doc (except the version-exempt ones the target's `CLAUDE.md` declares; absent a declaration, those the version-and-date principle in `MBT_PATTERN.md` exempts) opens with a well-formed `> V<N>, YYYY-MM-DD.` and no smuggled change-note.
3. **Cross-references** — every mini-brain filename mentioned resolves to a current canonical file, not an `archive/` copy or a deleted file. *Multi-lobe brain:* resolve against the lobe that owns the lobespace, not the repo root.
4. **Namespace prefix** — every top-level knowledge file and every `working/` doc carries the lobespace (`find . working -maxdepth 1 -name '*.md' 2>/dev/null | grep -vE '/(CLAUDE|README|CONTRIBUTING)\.md$' | grep -v '/<LOBESPACE>_'` should print nothing — it tolerates a missing or empty `working/` and anchors the lobespace to the start of the filename). *Multi-lobe brain:* run it per lobe against that lobe's declared lobespace, over the lobe's own documents and its `working/` — never its `archive/`, where retired files legitimately keep the basename they were retired under and need not be markdown. Match the lobespace exactly: a document belongs to the lobe whose lobespace its name begins with in full, longest match winning. Lobespaces nest as prefixes (`ORCHARD` inside `ORCHARD_PRESS`), so the prefix test above silently accepts a child's document sitting in its parent's directory. A brain seeded before working docs carried the brain's lobespace names its in-flight docs `working/<WORK>_*` by the then-current convention — treat that as adopt-when-touched guidance, not a violation, since renaming a live item's docs breaks the routing signals that match on those names.
5. **Log discipline** — the session log is append-only and readable from its last separator (not required to be read whole); entries carry a date and session identifier. Append-only governs each entry's content, not its position, so dates out of sequence are not a violation: work-item closeout preserves each merged entry's original date, and folding one log into another places entries by date among the existing ones. Check that no entry was revised after the fact, not that the file runs chronologically.
6. **Cross-lobe references** (multi-lobe brains) — cross-lobe references stay within the entrypoint's declared exemptions: a child's SCOPE may cite its parent's SCOPE, its APPROACH its parent's APPROACH, and any document may name its own child lobes — never their files. Any other reference to another lobe or its files is a violation, sibling references above all. Logs and maintenance documents are exempt — a log records what a session touched, and a procedure names the files it operates on.
7. **Vocabulary alignment** — grep the target's canonical docs, `CLAUDE.md` and `README.md` for the old pattern vocabulary: "unit" (pattern-specific sense: a brain's hub or any of its children), "token" (pattern-specific sense: the SCREAMING_SNAKE_CASE namespace), "component" (pattern-specific sense: a non-hub node), "component-structured" and `<TOKEN>` / `<SUBTOKEN>` / `<PREFIX>` placeholders. A brain seeded before the rename to "lobe" / "lobespace" uses the old terms in its own docs and `CLAUDE.md`. The rename doesn't break it — its internal vocabulary is self-consistent — but it creates a vocabulary split: the toolkit says "lobe" while the brain says "unit," and a session loading both sees two terms for one concept. Report the split as an opportunity. Where an old term also carries its ordinary sense elsewhere in the brain ("component" naming a lobe in `CLAUDE.md` and a software part in a knowledge document), the rename resolves that collision too, so report it here and not as a candidate enforced term. The rename below runs only in §5, when the user takes that step up. **Rename:** for each hit, classify it by surrounding context. *Unambiguous pattern-specific* (e.g. "the brain's token is `ORCHARD`") — replace silently: "unit" → "lobe", "component" → "lobe", "component-structured" → "multi-lobe", "token" (namespace sense) → "lobespace", `<TOKEN>` → `<LOBESPACE>`, `<SUBTOKEN>` → `<SUBLOBESPACE>`, and `<PREFIX>` → `<LOBESPACE>` except where it names a document that lives only at the hub (session closeout, work setup, work closeout, dream cycle), which takes `<HUB>`. A brain that defined `<PREFIX>` as a compound (e.g. `LOBESPACE_<WORK>`) rather than the bare lobespace needs the compound expanded to its concrete form — the `<WORK>` slot must survive the conversion, so the replacement is the expanded compound, not a simple rename to `<LOBESPACE>`. *Unambiguous ordinary-English* (e.g. "unit test", "auth token", "software component") — skip silently. *Genuinely ambiguous* — surface to the user to judge. Bump version headers on each file touched.

---

## 4. Report

Produce a written assessment. Structure it:

- **Summary** — the brain's stage, its lobespace (or its lobe tree and per-lobe lobespaces, if multi-lobe), and a one-line overall read (what kind of shape it's in).
- **What's working** — the principles it embodies well. Lead here.
- **Principle scorecard** — the table from §2 with each verdict and note.
- **Structural issues** — anything the §3 checks flagged, most-actionable first.
- **Substance issues** — drifted SCOPE claims, a scope or approach that has become a status report, an approach that names no second approach or leaves a goal unanswered, a scope that carries its design's choices, cross-document inconsistencies, a lobe whose scope no longer states one problem, enforced-term misuses, entry concerns and candidates, and pruning candidates, if any.
- **Recommended next steps** — ranked, concrete opportunities. Frame each as "this brain does X well but Y would help because …", tied to a principle. If a step is "adopt lifecycle machinery," name the specific machinery and point at the relevant `templates/` file.

Keep it proportionate: a healthy brain gets a short report that says so. Reserve length for real, actionable gaps.

---

## 5. Walk through

After the report, offer to walk the user through the recommended next steps in order. For each step they take up, make the change they approve, following the target's own `CLAUDE.md` conventions for every edit. Leave each step they decline as it stands. Do not commit unless the user asks.
